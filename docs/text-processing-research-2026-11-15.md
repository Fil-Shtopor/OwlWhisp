# Перевод и очистка диктовки: исследование и локальные эксперименты

Дата: 15 ноября 2026 года. Статус: исследование завершено; три независимые настройки
реализованы в Rust, по умолчанию выключены.

## Итог реализации и проверка нативного тракта

В **Settings → Text processing** добавлены удаление явных междометий, лёгкая правка
пунктуации/регистра и локальный перевод с выбором языка. Раскрываемая справка описывает
ограничения. Для очистки предусмотрены 17 языков и ручной выбор языка, когда короткий
или смешанный текст нельзя надёжно определить автоматически. Неоднозначные слова
вроде «ну», «типа», `like`, `那个` и `嗯` остаются. Пунктуация использует выход текущего
ASR и правила, без дополнительного классификатора: пропущенные запятые она не угадывает.

Повторная проверка собранного `lw-app` с **реальным установленным Hy-MT2/llama.cpp**
на той же машине, без других параллельных модельных замеров:

| Операция | Измеренное добавочное время |
|---|---:|
| Правила очистки и форматирования, короткая фраза, среднее 1 000 проходов | 0,0033–0,0034 мс |
| Перевод 8 коротких примеров, готовый процесс, CPU | 0,35–0,79 с |
| Те же примеры, RTX 4080 Laptop / CUDA | 0,054–0,147 с |
| Запуск и загрузка модели при прогретом файловом кэше, CPU / CUDA | 0,93 / 0,86 с |
| Возврат из уже истёкшего бюджета, CPU / CUDA | 1,10 / 0,19 мс |
| Реальный HTTP-таймаут с бюджетом 1 мс, CPU / CUDA | 2,29 / 1,52 мс |

Это отдельные smoke-замеры интеграции, а не новый многократный бенчмарк или оценка
качества всех языков. Время правил не включает создание конвейера, распознавание,
доставку текста и запуск приложения. Исходный эксперимент с длинным абзацем ниже
остаётся ориентиром: около 0,8 с на GPU и 4,5 с на CPU. Холодный файловый кэш, другое
железо и одновременно работающий ASR могут увеличить задержку.

Проверены RU→EN, EN→RU/FR/IT/ES/ZH, технические литералы и перевод цитируемой прозы.
Установка проверила SHA-256 имеющихся исследовательских архивов и весов, распаковала
их в отдельный тестовый каталог и запустила установленный runtime. Полная загрузка
сети в этой проверке не повторялась. Отдельно проверены отказ от слишком длинного
ввода, истёкший бюджет и завершение worker. Первоначально ожидание освобождения
страниц Windows добавляло 0,14–0,57 с к ошибочному переводу; оно перенесено в фон.

Бюджет перевода по умолчанию **5 с**, доступен выбор 1–30 с. Загрузка начинается
одновременно с записью; бюджет после ASR учитывает оставшуюся загрузку и сам перевод.
При ошибке, таймауте, усечённом ответе, изменении защищённого технического литерала
или вводе длиннее 3 000 символов вставляется очищенный исходный текст с объяснением
в Dictate. Изменённую расшифровку можно восстановить через **Copy original transcript**.
Переводчик выгружается по общему таймеру простоя; выключение с сохранением также
освобождает worker. Обмен текстом идёт по аутентифицированному loopback без HTTP-прокси.

Для правил **нет дополнительных весов**. В итоговой реализации добавляется только
переводчик; приведённая ниже сумма с отдельной ONNX-пунктуацией **не является её расходом**.
Исследовательский ориентир Hy-MT2 CUDA: 1 541 МиБ рабочего набора и примерно 1 590 МиБ
добавочной системной VRAM. Это сверх ASR; нативная оболочка и другие платформы могут
иметь другой расход. Весовой файл — 1 133 080 448 байт; вместе с архивами runtime
загрузка составляет 1,16 GB для Windows x64 CPU и 1,76 GB для CUDA. Распакованные
библиотеки занимают дополнительное место, исходные архивы сохраняются для повторной установки.

Проверки: [многоязычные ожидаемые результаты](../tests/fixtures/text-processing/multilingual-cleanup.json),
миграция старых настроек, все восемь комбинаций переключателей, защита кода и цитат,
отказ от небезопасных путей архива. Пройдено 325 автоматических тестов core/app/GUI,
два существующих ручных теста пропущены; `cargo check --workspace --all-targets` проходит.
GUI собран; визуальная проверка управления
не выполнена: оба доступных инструмента управления окнами не запустились в песочнице Windows.

Данные: [CPU](measurements/text-processing-2026-11-15/implementation-cpu.json),
[CUDA](measurements/text-processing-2026-11-15/implementation-cuda.json),
[воспроизводимый нативный эксперимент](../crates/lw-app/examples/text_processing_smoke.rs).
Из корня: `cargo run -p lw-app --example text_processing_smoke -- <scratch-settings.json> cpu`
(или `cuda`). Пример явно готовит локальный переводчик в тестовом каталоге; он может

задать `LW_APP_DATA_DIR` на тестовый каталог и запустить
`cargo run -p lw-gui --example text_settings_preview`.

## Дополнение: совместная память и вариант без дополнительной модели очистки

После вопроса о памяти выполнена отдельная проверка обоих предлагаемых текстовых
моделей одновременно. Для пунктуации исключены Transformers/PyTorch: использованы
только ONNX Runtime и нативный токенизатор.

| Компонент | Рабочий набор процесса после обработки | Видеопамять |
|---|---:|---:|
| Hy-MT2 CUDA | 1 541 МиБ | Весь запуск увеличил системное использование на 1 590 МиБ |
| Пунктуация ONNX CPU | 413 МиБ | CPU-исполнение |
| Сумма рабочих наборов | 1 954 МиБ ≈ 1,91 ГиБ | 1 590 МиБ ≈ 1,55 ГиБ |

Это исследовательские процессы, а не готовая интеграция в Rust. Сумма рабочих наборов
может повторно учитывать общие страницы DLL. GPU-дельта измерена системным nvidia-smi,
а не счётчиком конкретного процесса; после остановки worker использование вернулось
к исходному значению. К этим добавочным расходам относится отдельно память текущего ASR.
Private commit не равен резидентной физической памяти: у этих процессов он составил
около 2 325 и 1 135 МиБ соответственно.

[Данные совместного запуска](measurements/text-processing-2026-11-15/combined-text-memory.json),
[скрипт](../scripts/benchmarks/text_processing_memory.py).

**Уточнение прежней рекомендации:** Parakeet TDT v3 уже поддерживает пунктуацию и регистр
([карточка NVIDIA](https://huggingface.co/nvidia/parakeet-tdt-0.6b-v3)). Это упущено при
первоначальном выборе дополнительного пунктуационного классификатора. Проверка текущего
`lw.exe` на русском аудио вернула:

> Основной религией в Молдавии является православное христианство.

[Фактический вывод](measurements/text-processing-2026-11-15/asr-punctuation-check.json)
подтверждает сохранение регистра и точки текущим трактом. Один пример не оценивает
качество всей пунктуации, но отдельную модель по умолчанию добавлять пока незачем:
сначала следует измерить её улучшение относительно уже пунктуированного выхода Parakeet.
Для других ASR-моделей это свойство нужно проверять отдельно.

Также проверен узкий прототип правил: удаление отдельных `эм`, `э-э`, длинного `ээ`,
`um`, `uh` с сохранением фрагментов в кавычках/backticks. На 20 текстах, 5 сериях по
1 000 проходов, средняя стоимость одного текста имела медиану 7,68 мкс в Python.
[Проба и ответы](measurements/text-processing-2026-11-15/rule-cleanup-probe.json).
Это замер небольшого прототипа, не итогового Rust-кода и не оценка полноты очистки.
`ну`, `типа`, `как бы`, `значит` намеренно не удалялись: они часто содержательны.
Даже междометия требуют защиты цитат, кода и контекстов вроде названия буквы.

Уточнённый минимальный вариант: пунктуация и регистр от текущего Parakeet,
консервативное удаление явных междометий правилами, перевод отдельной опцией Hy-MT2.
Для первых двух операций дополнительные веса не требуются; полная смысловая очистка
по-прежнему не подтверждена.

## Решение

**Перевод стоит рассматривать как отдельную, явно включаемую функцию с Hy-MT2-1.8B Q4_K_M.**
На проверенной RTX 4080 Laptop готовый перевод коротких фраз получается примерно за
0,14–0,25 с, абзаца из 79 слов — за 0,78 с. Это добавочное время после получения
расшифровки, при уже загруженной модели. На CPU тот же длинный пример занимает 4,52 с:
быстрый универсальный режим для всех компьютеров этим результатом не подтверждён.

**Полную очистку с удалением слов-паразитов пока не рекомендую автоматически применять
перед вставкой.** Проверенные универсальные модели и экспериментальная конверсия
специализированного fine-tune допускали смысловые потери. Увеличение до 4B улучшает
пунктуацию, но не гарантирует удаления паразитов и сохранения всей диктовки.
На CPU 4B дополнительно занимает 13–15 с на длинном примере.

**Отдельная быстрая пунктуация технически осуществима:** небольшой ONNX-классификатор
работает за 21–45 мс на коротких/средних примерах и примерно за 126 мс на 95 словах.
Он не удаляет паразиты. Его опубликованный препроцессор также требует защиты технических
фрагментов перед использованием в OwlWhisp.

Это выбор лучших из проверенных вариантов, а не утверждение о лучшей модели вообще.
Промпты, модельные ответы, версии и измерения сохранены; приложение и его настройки
не подключены к экспериментальному серверу.

## Что и как проверялось

- Windows x64, Intel Core i9-13900HX, 24 физических ядра / 32 потока, около 64 ГиБ RAM.
- NVIDIA RTX 4080 Laptop, 12 282 МиБ VRAM, драйвер 617.14.
- Девять моделей: шесть исходных GGUF, Marian, пунктуационный классификатор и
  экспериментальная GGUF-конверсия Transcrib. Несколько вариантов промптов и beam search.
- 28 основных сценариев и 16 дополнительных проверок: всего 44 сценария на
  38 уникальных исходных текстах.
  Из них 20 — очистка, 18 — перевод, 6 — перевод с очисткой одним запросом.
  Длинный пример очистки адаптирует описание задачи пользователя.
- **1 248 учитываемых прогонов:** 1 217 повторных запросов и 31 первый запрос.
  Это повторения небольшой выборки, а не 1 248 разных текстов.
- `llama.cpp b12420`, GGUF Q4_K_M, контекст 4096, один слот, batch запросов = 1,
  восемь CPU-потоков. Для GPU — полная выгрузка слоёв в CUDA 13.5; для CPU — CPU-сборка
  и `-ngl 0`. Экспериментальный Transcrib экспортирован в Q8_0.
- Thinking выключен через `--reasoning off`. Генерация жадная, `temperature=0`, seed 42.
  Повторное использование префиксов отключено через `cache_prompt=false`; все учитываемые
  ответы с телеметрией показали `cache_n=0`.
- Измеряется **весь готовый ответ**, включая локальное применение chat template и HTTP,
  а не время до первого токена. У Marian/ONNX включены токенизация и декодирование.
  Загрузка, первые запросы и прогретые запросы учитываются отдельно.
- Обычно три повторения каждого текста; финальный перевод Hy-MT2 — пять повторений.
  Приведены медианы и наблюдавшиеся максимумы. Для устойчивого p95 выборки недостаточно.
- Никаких сетевых вызовов моделей: inference только на этой машине. Интернет использовался
  для документации и скачивания весов/инструментов.

Синтетические тексты содержат отрицания, числа, даты, пути, идентификаторы, вопросы и
инструкции, которые нужно сохранить как диктовку. Дополнительный набор создан после
первого скрининга. Для Hy-MT2 сохранён исходный промпт автора модели; проверки очистки
остаются исследовательскими, не формальным слепым тестом. Ответы просмотрены вручную;
профессиональная оценка переводчиками и большой корпус реальных диктовок не проводились.
Проценты «точности перевода/очистки» по этой выборке не рассчитывались.
Частоты CPU/GPU, план питания и фоновые процессы жёстко не фиксировались;
числа описывают эту настольную сессию, а не лабораторный аппаратный рейтинг.

Нет транспортных ошибок, пустых ответов или достижений лимита 512 выходных токенов
в учитываемых прогонах. **Это проверка выполнения запросов, не показатель качества текста.**

## Перевод: измерения и качество

Одинаковые три исходных русских текста: 8, 17 и 79 слов. В ячейках — медиана в мс
и максимум в скобках. Это готовый перевод при загруженной модели.

| Вариант | 8 слов | 17 слов, отрицания | 79 слов |
|---|---:|---:|---:|
| Marian INT8, CPU, beam=1 | 52 (56) | 92 (94) | 462 (465) |
| Marian INT8, CPU, beam=4 | 95 (95) | 163 (164) | 936 (939) |
| **Hy-MT2 Q4_K_M, CUDA** | **137 (146)** | **203 (209)** | **782 (799)** |
| Hy-MT2 Q4_K_M, CPU | 584 (591) | 1 066 (1 091) | 4 516 (4 692) |

Для Hy-MT2 использован рекомендуемый автором пользовательский промпт перевода,
без дополнительной системной роли. На 18 разных переводных примерах — основной набор
плюс восемь дополнительных — при ручном просмотре не обнаружено критической потери смысла.
Проверены RU→EN, EN→RU, RU→ES и ES→EN. Это не подтверждает качество всех заявленных языков.
В основном RU→ES примере осталась грамматическая ошибка `el traducción`; форматы дат
иногда локализовались, сохраняя дату.

На дополнительных примерах сохранены `user_id=42`, `/api/v2/users`, `threshold=0.02`,
`settings.toml`, имена, условность «возможно», «не уверен» и ограничения
«не раньше 18:45 / не позже 20:10». Инструкция «напиши только слово…» переведена как
содержание документа, а не выполнена.

Marian оказался существенно быстрее и меньше. Но в техническом примере:

- `/v1/chat/completions` превратилось в `/v1/chat/complements`;
- `v0.2.0` — в `v2.0` или `v.2.0`;
- beam=4 дополнительно исказил `enable_cleanup=false` в `enable_clearup=false`.

Beam search увеличил задержку примерно вдвое и не исправил эти проблемы.
В greedy-ответе время `14:30` стало `2:30` без указания половины суток.
Вариант `1,250` вместо `1250` сам по себе ошибкой значения не считался.
Marian может быть основой отдельного CPU-эксперимента с защитой терминов, но по этим
результатам не выбран для автоматического перевода технической диктовки.

## Очистка: почему одной скорости недостаточно

Для финального консервативного промпта задача сужена до удаления бессмысленных паразитов,
пунктуации и регистра: без пересказа, перевода и разрешения самоисправлений.
Таким образом, отрицательный вывод не основан только на дополнительных требованиях
к исправлению сказанного.

| Вариант | 7 слов | 21 слово | 95 слов |
|---|---:|---:|---:|
| Пунктуация/регистр, ONNX CPU | 21 мс | 34 мс | 126 мс |
| Qwen3.5-2B, CUDA, консервативный промпт | 190 мс | 253 мс | 985 мс |
| Qwen3.5-4B, CUDA, консервативный промпт | 292 мс | 465 мс | 1 840 мс |
| Qwen3.5-4B, CPU, локализованный промпт* | 3 104 мс | 3 887 мс | 13 722 мс |

\* CPU-строка использует другой, явно записанный в данных промпт; это иллюстрация
стоимости CPU-генерации, а не строгое сравнение одного и того же ответа с CUDA.
У CPU-длинного примера наблюдавшийся максимум — 14 992 мс.

Существенные ошибки:

- Qwen3-0.6B сокращал «привет, давай созвонимся завтра утром» до «привет утром завтра».
- Qwen3.5-0.8B отвечал на продиктованный вопрос вместо перевода, а часть переводов
  оставлял на исходном языке.
- Qwen3.5-2B даже с консервативным промптом менял «эм» на «эмодзи» в длинном тексте
  и возвращал только «банан» или «готово», выполняя инструкцию внутри диктовки.
- Qwen3.5-4B часто улучшал пунктуацию, но оставлял «эм», «ну», «короче».
  В основном инструкционном примере консервативный промпт также давал только «банан».
  На дополнительном примере с другой формулировкой поведение было лучше: проблема
  зависит от текста и не устраняется одним общим промптом.
- Однопроходный перевод + очистка проверен на шести примерах. На обычных сообщениях
  он быстр, но в некоторых промптах превращал поправку «во вторник, нет, в среду»
  в «во вторник, не в среду». Эти самоисправления были дополнительным стресс-тестом.

### Специализированный Transcrib

Автор заявляет русский среди языков fine-tune Qwen3-0.6B. Опубликован только
MLX INT4. Для эксперимента на Windows выполнена распаковка affine INT4 group=64 в BF16
и экспорт через закреплённый конвертер llama.cpp в Q8_0.
[Рецепт и хеши](measurements/text-processing-2026-11-15/transcrib-conversion.json) сохранены.

У опубликованного токенизатора отсутствует chat template. Первые прогоны с fallback
ChatML исключены; затем использован шаблон исходного Qwen3 с выключенным thinking.
В исправленном запуске длинный текст всё равно сокращался до первого предложения,
«два плюс два» менялось на «три плюс четыре», а в дополнительном примере исчезала
часть «возможно, мы успеем к четвергу». Быстрая генерация неполного ответа не считается
успешной оптимизацией.

**Это результат экспериментальной конверсии, не проверка исходного MLX на Apple silicon.**
Паритет с оригинальным MLX-запуском не установлен; такой артефакт не рекомендован к поставке.

### Быстрый классификатор пунктуации

Horizon Labs даёт нужный порядок задержки без генерации полного текста по токенам.
Но он сохраняет паразиты, например «Эм, привет. Ну, давай…». Ошибки пунктуации также
остаются: «два плюс два» в одном примере разделено точкой с последующим вопросом.

`config.json` превратился в `configjson` из-за удаления точки **опубликованным
препроцессором**, а не из-за генерации нового имени моделью. Перед применением нужно
сохранять технические фрагменты и исходные символы при восстановлении текста.
Нельзя просто подключить демонстрационный helper к вставке. Это кандидат на отдельную
опцию «пунктуация», но не реализация полной очистки из запроса.

## Загрузка и память

Медианы выше относятся к загруженной модели. При запуске процесса Hy-MT2 CUDA готовность
заняла 1,12 с, первый короткий запрос — ещё 0,14 с. У 4B готовность в финальных запусках
составляла около 2,0–2,2 с. Это перезапуск процесса с уже доступными DLL и прогретым
файловым кэшем, а не проверка после перезагрузки Windows или холодного чтения с диска.

В Python-базовых вариантах отдельно измерены:

| Вариант | Импорт зависимостей | Подготовка модели и токенизатора после импортов |
|---|---:|---:|
| Marian / CTranslate2 | 11,87 с | 3,71 с |
| Пунктуация / ONNX | 12,75 с | 4,28 с |

Импорты Python не являются обязательной стоимостью будущего Rust-продукта; скорость
нативной загрузки этих вариантов в OwlWhisp не измерена. Запуск Python после каждой
диктовки заведомо уничтожил бы преимущество короткой обработки.

У Hy-MT2 CUDA лог показывает 1 075,74 МиБ буфера весов и 56,01 МиБ compute-буфера;
у 4B — 2 603,50 и 78,02 МиБ соответственно. Это **не вся VRAM**: сюда не включены
все остальные буферы, KV cache и стоимость драйвера. Максимум из снимков private commit
worker-процесса после запросов: Hy-MT2 CUDA около 2 325 МиБ, 4B около 4 175 МиБ.
Python-базовые процессы также загружают тяжёлые исследовательские библиотеки;
их память нельзя выдавать за будущий расход Rust-клиента.

Практический вывод: дополнительную модель нужно готовить при начале записи и держать
в отдельном worker с управляемым idle timeout. Цена постоянной готовности — память.
Включать такую модель для всех пользователей по умолчанию без локального бенчмарка
не соответствует цели лёгкого клиента.

## Связь с текущим OwlWhisp

В рабочем `build_pipeline` сейчас находятся нормализация whitespace/NFC и словарь.
`LlmProcessor` в `lw-core` существует, но из `lw-app` не подключён. Он синхронный,
предполагает OpenAI-compatible endpoint и имеет стандартный timeout 15 с. Это заготовка,
а не готовая низколатентная функция очистки. Выбор языка распознавания также не является
настройкой языка перевода.

Существующий CPU-бенчмарк `lw.exe` на трёх русских FLEURS-клипах длительностью
5,64–7,50 с дал 2 865 / 3 007 / 3 061 мс распознавания после отдельного прогрева.
Загрузка engine — 2 496 мс. Это отдельная контрольная серия
([вывод](measurements/text-processing-2026-11-15/asr-final-cpu.txt)); задержки VAD,
микрофона, буфера обмена и реальной вставки здесь не измерялись.

Полезная модель времени:

`последнее слово → вставка = завершение записи/VAD + ASR + текстовая обработка + доставка`

В этом исследовании отдельно измерен новый текстовый этап. Сквозной прототип с обоими
одновременно резидентными моделями ещё нужен перед включением функции в продукт.
Обещать по этим данным полную задержку «от отпускания клавиши до вставки» нельзя.

Рекомендации для следующего этапа разработки:

1. Независимая, выключенная по умолчанию опция перевода: `Off` / язык результата.
   Hy-MT2 — первый кандидат для этой машины; выбор языка ограничить поддержкой конкретной модели.
2. При подготовке модели выполнить локальный бенчмарк. Предварительный инженерный ориентир:
   до 0,5 с на короткое сообщение, около 1–1,5 с на длинный абзац. Это предложенный бюджет,
   не согласованное пользователем требование и не результат для всех устройств.
3. Жёсткий ограниченный срок ожидания текстового этапа, сохранение исходной расшифровки,
   понятный статус при невозможности получить перевод. Нельзя молча выдавать исходный
   язык за успешный перевод или принимать обрезанный ответ как готовый текст.
4. Для полной очистки — сначала специализированное обучение/оценка на русских реальных
   диктовках или модель KEEP/DELETE с восстановлением исходных слов. Крупная универсальная
   LLM по этим экспериментам не решает задачу достаточно надёжно.
5. Отдельно можно изучать безопасную пунктуацию с защитой технических фрагментов.
   Не удалять «ну», «типа», «как бы» глобальными регулярками: они бывают содержательными.

## Воспроизведение и данные

Бинарники, веса, venv и промежуточные конверсии находятся в игнорируемом
`.owlwhisp-test/text-processing/`. В git-подготовленные материалы включены только
скрипты, фикстуры, метаданные и текстовые результаты.

Основные файлы:

- [summary.json](measurements/text-processing-2026-11-15/summary.json): статистика всех серий,
  количество запросов, исключённые прогоны, SHA256 исходников и фикстур.
- [outputs.md](measurements/text-processing-2026-11-15/outputs.md): исходные тексты,
  примерные эталоны и ответы моделей для ручного сравнения.
- [raw/](measurements/text-processing-2026-11-15/raw/): полные JSONL с ответами, временем,
  параметрами, памятью и подтверждением выгрузки на GPU.
- [scripts](../scripts/benchmarks/text_processing_research.py),
  [CPU-базовые модели](../scripts/benchmarks/text_processing_baselines.py),
  [экспериментальная конверсия](../scripts/benchmarks/convert_transcrib_research.py),
  [сборка отчётных данных](../scripts/benchmarks/summarize_text_processing.py).

PowerShell, из корня репозитория:

```powershell
uv venv --python 3.11 .owlwhisp-test/text-processing/venv
uv pip install --python .owlwhisp-test/text-processing/venv/Scripts/python.exe `
  --torch-backend cpu -r scripts/benchmarks/text-processing-requirements.txt
$env:PYTHONUTF8 = '1'
$benchPython = '.owlwhisp-test/text-processing/venv/Scripts/python.exe'

& $benchPython scripts/benchmarks/text_processing_research.py prepare `
  --manifest docs/measurements/text-processing-2026-11-15/manifest.json
& $benchPython scripts/benchmarks/text_processing_research.py run `
  --model hymt2-18b --backend cuda --tasks translation --repeats 5 `
  --output .owlwhisp-test/text-processing/reproduced-hymt-cuda.jsonl
& $benchPython scripts/benchmarks/text_processing_research.py run `
  --model hymt2-18b --backend cpu --tasks translation `
  --fixtures tests/fixtures/text-processing/holdout.json --repeats 3 `
  --output .owlwhisp-test/text-processing/reproduced-hymt-holdout-cpu.jsonl

& $benchPython scripts/benchmarks/text_processing_baselines.py prepare
& $benchPython scripts/benchmarks/text_processing_baselines.py run `
  --model marian --beam-size 1 --repeats 3 `
  --output .owlwhisp-test/text-processing/reproduced-marian-cpu.jsonl
& $benchPython scripts/benchmarks/text_processing_baselines.py run `
  --model punct --repeats 3 `
  --output .owlwhisp-test/text-processing/reproduced-punct-cpu.jsonl
```

Для консервативной очистки выбрать `--model qwen35-2b` или `qwen35-4b`,
`--tasks cleanup --prompt-style conservative`. Для экспериментального fine-tune сначала
запустить `convert_transcrib_research.py`, затем передать `--model qwen3-06b`,
`--model-file .owlwhisp-test/text-processing/models/Transcrib-Cleanup-0.6B-Q8_0.gguf`,
`--model-label transcrib-06b` и `--chat-template-file
docs/measurements/text-processing-2026-11-15/transcrib-chat-template.jinja`.
Запуски моделей выполнять последовательно; во время замеров не выполнять другое inference.

Числа из старых `marian-init-cpu` / `punct-init-cpu` исключены из итогов: серия подготовки
пересеклась с первоначальной ASR CPU-проверкой. Обе серии затем повторены последовательно.
Неисправленные template-прогоны Transcrib также исключены. Причины записаны в summary.

Вспомогательные первичные источники: [рекомендации CTranslate2 по CPU/INT8/beam size](https://opennmt.net/CTranslate2/performance.html),
[API и параметры llama.cpp server](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md),
[документация MLX dequantize](https://ml-explore.github.io/mlx/build/html/python/_autosummary/mlx.core.dequantize.html).

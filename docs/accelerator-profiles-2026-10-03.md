# Проверка профилей ускорителей — 3 октября 2026

TensorRT стоит сохранить как дополнительный режим для Parakeet. После устранения
пересборок движка и полного прогрева он оказался быстрее CUDA на этой машине.
Для обычного запуска NVIDIA предпочтение остаётся у CUDA: первая подготовка TensorRT
требует около двух минут и дополнительного места для кэша.

## Условия

- Windows x64, Intel Core i9-13900HX, RTX 4080 Laptop GPU, 12 ГБ, NVIDIA 617.14.
- Питание от сети, Legion Performance Mode; приложение оставалось открытым, замеры
  ускорителей выполнялись последовательно.
- Parakeet TDT 0.6B v3; одни и те же 12 FLEURS WAV на en/ru/es/uk, 5,10–7,92 секунды.
  Три китайских записи пропущены, поскольку модель не заявляет китайский язык.
- GPU используют обычный динамический FP32 ONNX-энкодер; TensorRT может выбирать FP16
  kernels. CPU использует отдельный INT8-энкодер. Поэтому разница WER между CPU и GPU
  не доказывает разницу точности самих провайдеров.
- ONNX Runtime GPU 1.28.0, TensorRT 10.14.1.48, отдельный Windows ML runtime для DirectML.

Это локальные измерения RTX 4080. Они не заменяют эталонные показатели ASUS Zenbook A16
в каталоге и не записывались в его reference RTF/accuracy.

## Два разных режима измерения

Первый проход по разным длинам включает подготовку новых форм и выбор GPU-ядер.
Исключение только первого клипа не делает остальные формы полностью прогретыми.
Это было особенно дорого у TensorRT без явного профиля, но заметно и у CUDA.

Второй режим сначала распознаёт все допустимые клипы без таймера, затем измеряет их
на том же движке (`lw bench --warm-up`). Подготовка и загрузка сессий печатаются отдельно.
Он измеряет установившуюся скорость на этих формах, а не задержку первого использования
произвольной новой длины.

| Провайдер | RTF полного измеренного прохода после прогрева всех форм | WER | Повторы |
|---|---:|---:|---:|
| TensorRT, новый профиль FP16 | **0,0077–0,0097** | 5,4% | 2 |
| CUDA | 0,0246–0,0275 | 5,4% | 2 |
| WebGPU | 0,0204–0,0293 | 5,4% | 2 |
| DirectML | 0,0356–0,0362 | 5,4% | 2 |
| CPU, INT8 | 0,1879 | 3,0% | 1 |

Таким образом, на подготовленном проходе TensorRT примерно в три раза быстрее CUDA.
Это преимущество измерено на RTX 4080 Laptop, без RTX 5090. Разброс WebGPU не позволяет
уверенно ранжировать его относительно CUDA по этим двум прогонам.

После загрузки новой сессии, без предварительного прохода по всем формам, среднее RTF
клипов после первого было 0,0523–0,0614 у широкого TensorRT FP16, 0,1230–0,1340 у CUDA,
0,0405–0,0421 у DirectML и 0,0445–0,0494 у WebGPU. Эти числа описывают другой режим.

## Профили TensorRT

Изначальное подключение через V2 не применяло устаревшие `ORT_TENSORRT_*` переменные.
Пробный запуск с ними фактически сохранил адаптивный профиль: шесть разных длин
потребовали 30–48 секунд каждая, а уже подготовленные длины — 74–167 мс. Его общий RTF
3,3601 отражает в том числе пересборки. Поэтому настройки теперь передаются прямо в
provider options; диагностические варианты используют `LW_TENSORRT_*`.

| Вариант | min / opt / max mel frames | Загрузка с первой компиляцией | Повторная загрузка | Кэш | WER |
|---|---|---:|---:|---:|---:|
| Широкий FP32 | 32 / 600 / 2000 | 69,95 с | 6,59 с | 2,49 ГБ | 5,4% |
| Широкий FP16 | 32 / 600 / 2000 | 158,27 с | 4,50 с | 1,25 ГБ | 5,4% |
| Узкий FP16 | 400 / 640 / 800 | 155,16 с | 4,70 с | 1,25 ГБ | 5,4% |
| **Профиль приложения FP16** | **1 / 600 / 2000** | **135,53 с** | **3,80–4,83 с** | **1,25 ГБ** | **5,4%** |

Узкий профиль не дал устойчивого выигрыша. Профиль приложения покрывает все окна,
включая короткий остаток длинной записи. Формы: `audio_signal:1x128xT,length:1`.
Максимум берётся из того же ограничения, которым движок делит длинную речь на окна;
значение по умолчанию — 2000 frames, около 20 секунд. Кэш timing хранится вместе с engine.

Дополнительно проверены записи 0,25 / 0,5 / 1 / 2 / 12 / 18 / 60 секунд, полученные
обрезкой или повторением локального en_1. Все допустимые записи прошли; размер кэша
остался 1 251 310 818 bytes. Показатели ошибок совпали с CUDA. Это проверка диапазона
форм и chunking, а не дополнительный независимый корпус для оценки точности. Искусственно
повторённая речь имеет большие ошибки из-за декодирования и удаления перекрытий.
Отдельный 10-миллисекундный WAV не прошёл CPU mel-frontend из-за reflect padding;
он короче допустимых 0,25 секунды записи приложения и не вошёл в сравнение ускорителей.

Механизм профилей и условия пересборки описаны в
[ONNX Runtime TensorRT EP](https://onnxruntime.ai/docs/execution-providers/TensorRT-ExecutionProvider.html#explicit-shape-range-for-dynamic-shape-input).

## Что поддерживать

| Путь | Решение | Основание |
|---|---|---|
| CPU | Обязательный базовый путь | Работает без GPU; остальные семейства моделей этой сборки используют sherpa CPU |
| CUDA | Основной NVIDIA путь | Быстрый старт и хорошая скорость после подготовки ядер |
| DirectML | Основной общий GPU путь Windows | Реальное распознавание проверено; подходит для охвата GPU разных производителей, скорость на AMD/Intel ещё надо измерить |
| WebGPU | Сохранить для переносимости | Реально проверен на RTX и ранее на Adreno; скорость зависит от GPU и формы |
| TensorRT | Дополнительный режим с подготовкой | Лучший подготовленный результат здесь, но нужен большой кэш и длительная первая компиляция |
| QNN / Qualcomm NPU | Основной путь Snapdragon для проверенных артефактов | Есть отдельные реальные измерения на ASUS Zenbook A16 / X2, см. docs/benchmarks.md; на текущей машине NPU нет |
| OpenVINO / Vitis AI / CoreML | Продолжать считать непроверенными на целевом оборудовании | Этот эксперимент ничего не измерял на Intel NPU, AMD NPU или Apple Silicon |

Проверка GPU-провайдеров здесь относится к Parakeet 0.6B v3. Наличие CUDA или DirectML
не делает остальные модели каталога ускоренными автоматически. Для каждой пары
модель/провайдер нужен совместимый граф и успешный запуск.

Текущий набор TensorRT DLL содержит builder resource для Ada SM 8.9. Результаты
не подтверждают готовность этой сборки для RTX 5090 или других GPU-архитектур.
При расширении поддержки потребуется проверить соответствующие runtime resources.

## Воспроизведение и изменения

Скрипт создаёт hardlinks на неизменённые файлы модели и отдельный кэш каждого профиля:

```powershell
cargo build --offline --release -p lw-cli
powershell -File scripts/benchmarks/compare-tensorrt.ps1 -Profile trt-dictation-fp16
powershell -File scripts/benchmarks/compare-tensorrt.ps1 -Profile trt-default -WarmUp -Label prepared
powershell -File scripts/benchmarks/compare-tensorrt.ps1 -Profile cuda -WarmUp -Label prepared
powershell -File scripts/benchmarks/compare-tensorrt.ps1 -Profile directml -RuntimeDir runtime/win-x64-directml -WarmUp -Label prepared
python scripts/benchmarks/summarize-tensorrt.py .owlwhisp-test/tensorrt-study-v2
```

Локальные логи и options JSON находятся в `.owlwhisp-test/tensorrt-study-v2/`; исходная
проверка игнорируемых переменных — в `.owlwhisp-test/tensorrt-study/`. В проверке
`trt-default` использована копия кэша точного профиля 1/600/2000, созданного выше на
тех же весах, GPU и runtime; запуск шёл без диагностических overrides и не пересобрал кэш.

В код перенесены FP16 и широкий профиль Parakeet, добавлены отдельное время загрузки
в CLI и режим `--warm-up`. TensorRT перенесён в конец общего порядка выбора GPU,
чтобы обычный запуск не начинал многоминутную компиляцию автоматически. Явный выбор
TensorRT и рекомендация по измеренному результату остаются доступны. Справка в Settings
обновлена: прежнее утверждение о неизбежном проигрыше CUDA больше не соответствует замерам.

Проверки: 20 тестов Parakeet, 13 тестов lw-ort и 9 тестов политики ускорителей прошли;
два теста lw-ort, требующие отдельного runtime-пуска, остаются штатно ignored.
Реальный runtime проверен описанными CLI-прогонами.
